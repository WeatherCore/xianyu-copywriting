# 反面案例：一份真实跑偏的文案是怎么写出来的

来源：`Spring-闲鱼文案-v1完整版.md`（Skill 生成，作者本人审查后判定"写得很乱，突出不了笔记含金量，完全不同于黄金案例"）。对应 PDF：377 页 Spring 课程笔记。

记录它，是因为**这份失败案例精确指出了 SKILL.md 旧版规则的结构性缺陷**——它写得"合规"，只是规则本身让模型无路可走。每一条后面都附了实测数据。

## 二、八条错误写法（对着改）

### 1. 把 API 文档抄进正文

❌ 原文（178 字）：
`生命周期 11 步：构造器 → 属性注入 → Aware 回调 → postProcessBeforeInitialization → afterPropertiesSet → init-method → postProcessAfterInitialization → 入 singletonObjects → @PreDestroy → DisposableBean → destroy-method`

✅ 同一知识点该这么写：
`生命周期：实例化、属性注入、初始化、销毁四大阶段，BeanPostProcessor 全程可插拔`

**病因**：规则只说"技术点名词必须来自 PDF 原文"，没说"名词是索引、讲解是中文"。模型照抄类名最安全，于是整条变成签名串。

### 2. 冒号右边塞参数详解

❌ `Debug 看容器四大件：beanFactory（DefaultListableBeanFactory）、beanDefinitionMap（存 BeanDefinition）、singletonObjects（单例池）、beanDefinitionNames（所有 bean id）`

✅ `Debug 看容器四大件：BeanFactory、BeanDefinition 映射、单例池、名称列表`

**实测**：黄金案例括号内文字只占子弹总字数 0%–2.1%；v1 是 **6.9%**（71 个括号）。括号成了躲避"讲人话"的通道。

### 3. 用 `→` 代替叙述

❌ `阶段1 扫描包：HspSpringApplicationContext(Class configClass) → @ComponentScan → replace(".","/") → getResource → listFiles → 截类名拼全路径 → loadClass 判定`

✅ `阶段一扫描包：读扫描路径、转成目录、遍历类文件加载成 Class`

箭头本身不是错（Maven 案例用了 11 次），错在**它被用来承载整条逻辑**——读者看到的是流水线代号，不是知识。

### 4. 拿英文缩写当术语密度

❌ `自动装配与 SpEL：autowire 的 no/byName/byType/constructor/default 五种模式与 primary、autowire-candidate 冲突解法`

✅ `自动装配五种模式：按名、按类型、按构造器全覆盖，冲突交给首选标记破解`

**关键**：v1 **不是术语太少，是术语质量太差**。它有 78% 的条含中文术语，但被 5 个一组的枚举词淹没了。黄金案例每条例词中位 **1–2 个**——一个精确的名词 + 一句人话解释，这才叫专业。

### 5. 模块数硬凑

PDF 只有 5 个大章（基本介绍 / 配置管理 bean / AOP / 手写底层 / JdbcTemplate 与事务），SKILL.md 旧规要求"8-11 个模块"，于是拆成 11 块，每块还得填 8 条 → 87 条。

✅ 按章节自然切片：这份 PDF 用二级标题（33 个）能切出 9–11 个模块；切不出就少写，**绝不把一条子弹拆成两条凑数**。

### 6. 单条被"讲透"绑架

v1 最长 178 字，因为模型想"把知识讲完整"。但这是**商品详情页不是教材**：

- 黄金案例单条 p90 只有 44 字
- 唯一超 100 字的是 Docker 的"八大指令逐句拆解"，属于无法拆分的并列清单，且全案仅此一条

✅ 一条只讲一个点，讲不完的放下一模块。

### 7. 首段膨胀

v1 首段 308 字（黄金案例 153–226 字）。塞进了 PDF 页数、六章节全名、每一章的细目，读起来像目录。

✅ 首段是**钩子**不是摘要：从痛点写法到容器接管，一句话讲清"这份笔记解决什么"。

### 8. 自检门禁只查结构不查手感

旧版 9 项门禁全是"段落齐不齐、模块数够不够、关键词几个"，**没有一项能量出"是否写成 API 大纲"**。所以 v1 逐项通过、作者本人一眼判死。

✅ 门禁改成 `scripts/gate.py` 机器体检 + 一句人话判断（见下）。

## 三、作者本人对 v1 的三条判词

原话：

1. 「生成的文案是不是有点太多英文那些单词什么的了，是不是有点不太专业」
2. 「我自己审查那个文案都感觉写的好乱，完全突出不了这份笔记的含金量」
3. 「完全不同于那些黄金案例」

对应到可执行规则：

- **不专业** → 英文词数不是关键，**术语是否有解释**才是。一条一个名词 + 中文释义。
- **写得很乱** → 符号噪音（括号、箭头、签名串）让读者无法扫读。冒号右边必须是散文。
- **突出不了含金量** → 含金量不在罗列了多少 API，在**点破难点**（容器结构、代理链、事务传播失效这些"卡壳处"）。挑难点讲，比穷举名词更像内行。

## 四、给模型的判断句

写完一条子弹，问自己：

> **「一个只会用 Spring 但不懂原理的人，读完这条能多懂一点吗？」**

答"能" = 这条值钱；答"只是把类名排了一遍" = 照第 1–4 条错误改。
